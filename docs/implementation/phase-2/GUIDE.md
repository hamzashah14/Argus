# Phase 2 — customer-owned infrastructure and release workflow

Status: repository implementation passes local verification. **G2 requires live
staging evidence and has not passed.** G1 hosted CI also remains pending. All
reference inputs are synthetic; no AWS resources were created in this phase.

## Architecture and boundaries

Use the strict `infra/deployment.schema.json` inventory. Copy the example into
ignored `.local/` for real deployment; keep account IDs, recipient addresses,
customer log fixtures, bindings, receipts and generated plans private. The example
has `reference_only: true`; cloud commands refuse it before authenticating.

| Stage | Region | Ownership and updates |
|---|---|---|
| foundation-tools | Bedrock | Private versioned artifact bucket, retained cursor secret, read-only CI role |
| foundation-monitor | Monitoring | Separate artifact bucket, retained log groups/topics, Nginx metric filters, ingestion/notification role boundaries |
| tools | Bedrock | New release-specific log/metric functions, numeric versions, agent, exact invoke grants and per-release roles; create only |
| alias | Bedrock | New alias on a prepared release-specific agent; creates a numbered agent snapshot; create only |
| worker | Monitoring | New trigger function/version, exact candidate alias policy, SNS grant and dispatcher role boundary; create only |
| routing | Monitoring | Stable EventBridge rule, inventory alarms, owned subscriptions and UI role; separately reviewed promotion |

Names include project/environment. Release stacks and functions also include
release_id. Global S3 names include account/region/purpose. Same-region deployments
still use two artifact buckets; split-region deployments never use cross-region
CloudFormation exports. Exact output ARNs/IDs are carried in private bindings.
The current generator supports commercial AWS regions and up to ten instances;
large inline templates fail locally at 51,200 bytes. This is not a fleet-scale IaC
system yet. Shorten the project name if a physical resource exceeds AWS name limits.

Log paths are `/<project>/<environment>[/<log_segment>]/<instance>/<service>`.
CloudWatch Agent files, metric descriptors and alarms come from the same inventory.
Container log drivers must be changed to these generated group names by the operator.
CWAgent/Nginx installation and application rollouts are not performed by this tool.
The process descriptor includes exe and pid_finder; confirm exact published
CloudWatch dimensions in staging before promotion.

## Roles and bootstrap prerequisites

The customer supplies **three existing, distinct roles** in the target account:
ui_principal_arn, ci_principal_arn and deployment_role_arn. The first two are trusted
workload/CI identities, not admin identities. The last is a CloudFormation service
role trusted by `cloudformation.amazonaws.com`; it is never assigned to a Lambda
or the UI. Choose separate staging/production accounts where possible.

Bootstrap these identities through the customer's existing IAM process. Do not
supply an administrator role to the web UI or CI. The deploying operator needs
scoped CloudFormation change-set/stack inspection, execution, sealing and output
permissions, `iam:PassRole` only for the selected CloudFormation role, plus the
read/upload/secret-version metadata operations used by the explicit CLI commands.
Candidate verification additionally needs Lambda/agent configuration reads and an
explicitly authorized `bedrock:InvokeAgent` canary. This project does not grant
those operator permissions automatically.

The CloudFormation role needs service actions for resources in the reviewed
plan only: project/environment S3 buckets/objects, SNS topics/subscriptions, Logs
groups/filters, alarms/rules, candidate Lambda resources, candidate Bedrock agents,
the cursor secret, and IAM roles under `/<project>/<environment>/`. Restrict
PassRole to those runtime roles and their intended service. Exclude unrelated
resources and restrict mutating actions to the selected regions. Customer IAM
review and negative live policy tests remain required before deploying this role.

Runtime boundaries generated by the templates:

- Logs role: exact inventory log ARNs; query-results/stop/discovery actions use
  wildcard Resource only where needed, with the monitoring-region condition.
  Only this role reads the exact pinned cursor secret ARN.
- Metrics role: GetMetricStatistics in the monitoring region. AWS metric reads
  cannot enforce per-instance dimensions through these IAM resources; the handler
  enforces the packaged allowlist. Separate accounts provide a stronger boundary
  if direct access by a compromised runtime must be isolated.
- Agent role: exact tool versions (or explicit release-name fallback) and exact
  operator-selected model/profile ARNs. No broad model wildcard.
- Worker role: exact candidate agent alias and report topic; own log stream writes.
  It still publishes directly in the pre-Phase-3 runtime.
- Ingestion, dispatch and notification roles are separately defined for Phase 3
  bindings: SendMessage to the environment incident-queue ARN, InvokeFunction on
  the candidate worker version, and Publish on the report topic respectively.
  **The queue and those runtime bindings are not implemented by these roles.**
- UI role: InvokeAgent on the promoted alias only. CI validation role: limited
  stack inspection and versioned artifact reads. No application role can deploy
  infrastructure or assume the CloudFormation deployment role through these policies.

No runtime receives broad S3 evidence or KMS permissions. Evidence storage and its
key policies remain Phase 3 work. Artifact buckets use versioning, public-access
blocking, bucket-owner enforcement, encryption and a deny for non-TLS access.
The cursor secret uses Secrets Manager's default encryption; a private artifact
contains only its ARN and VersionId, never its value. Customer-managed KMS keys
and enterprise identity controls require their later security review.

## Local preparation (no AWS calls)

```bash
.venv/bin/python -m pip install --require-hashes -r requirements/dev.lock
.venv/bin/python -m infra render --spec infra/deployment.example.json --output .local/phase2/reference-plan
.venv/bin/python scripts/validate_infrastructure.py
.venv/bin/python -m pytest
.venv/bin/python -m infra build --spec infra/deployment.example.json --output .build/reference-lambda --wheelhouse .build/wheels
```

The wheelhouse is created with the Phase 1 hash-verified pip download command.
The build packages both generated metric catalog and log scope. Use a separate
private output directory for a customer's inventory. `.local/` and `.build/` are
ignored; never commit a real generated bundle or raw cloud response.

A render emits template files, bundle.json, catalog/log scope and one CWAgent
configuration per instance. bundle.json records source SHA/dirty state, schema and
prompt hashes, artifact/source/SDK hashes, immutable S3 versions, account/regions,
model, role boundary, bindings and every template hash. Read the exact plan before
using its review_hash. Cloud change sets require a committed source checkout.
Editing a template after review invalidates the bundle.

## Staging workflow (creates resources and incurs customer AWS costs)

These commands are instructions for a future approved deployment, not a record
of actions already performed. First select actual account/regions, supported
Bedrock model/profile and exact model ARNs, fleet, IAM roles, recipient and budget.
Set `reference_only: false` only in that reviewed private configuration. Check
instance telemetry, chosen-model access, regional quotas and subscription ownership.
The previously inspected account had Lambda concurrency 10; a reservation of two
would fail. `reserved_concurrency: null` uses unreserved capacity and is **not a
spend cap**. Zero requires maintenance_mode, which disables automatic ingress.

1. Render foundations from a clean commit into a private directory. For each stage,
   use `change-set`, wait until the change set is ready, then `inspect`. Review the
   returned resource diff and hash before `execute`. Each command requires the
   exact bundle `--review-hash`. Execution additionally requires the inspected
   `--change-set-hash` and change-set ARN. The CLI verifies account, region, stack
   ownership, template and CloudFormation role. There is no auto-execute default.
2. Wait for both foundation stacks to complete. An EXECUTION_REQUESTED result is
   not deployment success. Use AWS stack events for diagnosis; keep raw output private.
3. Build against the **real private inventory**. Run `upload` with that spec/build
   directory. It checks bucket owner, region and versioning, verifies local package
   hashes, then stores objects under release ID/content hash and captures VersionIds.
   Existing candidate stack IDs are refused. Upload also pins the cursor secret
   version with a release label for retention across rotation.
4. Render again with `--build-dir` and uploaded `--bindings`. The tools stage now
   exists. Review/execute its CREATE change set and wait for CREATE_COMPLETE.
5. `collect --stage tools` merges stack outputs into a new bindings file. Run
   `prepare-agent` against those bindings. Preparation is explicit and bounded;
   failed/timed-out preparation leaves the active agent untouched. Render with
   the collected bindings to obtain the alias template, deploy it, then collect
   `--stage alias`. Omitted alias routing asks Bedrock to snapshot the prepared
   candidate; live verification must confirm one numbered version, never DRAFT.
6. Render/deploy the worker stage with the candidate agent/alias bindings. Collect
   `--stage worker`, then render the final complete bundle. The worker is not yet
   subscribed to incident ingress.
7. Run `seal --stage tools`, `seal --stage alias`, and `seal --stage worker` after
   creation. Sealing sets a deny-all-updates stack policy plus termination
   protection, then reads both back. Verification refuses unsealed releases.
8. Run `verify-candidate --invoke-canary` on the final bundle. **This invokes a paid
   model investigation.** It verifies immutable code/runtime/environment,
   numbered agent routing, model/prompt/schema/executor bindings, required metric
   descriptors, filter fixtures and concurrency, then requires actual successful
   observations from both tools. The receipt expires after one hour and is bound
   to this exact bundle. A refusal is not permission to bypass the gate.
9. Generate `retirement-plan`. Review exact stack-owned alarms/subscribers. For a
   nonempty plan, `retire --retirement-plan ... --receipt ...` disables obsolete
   alarm actions and unsubscribes retired recipients before cleanup. It rechecks
   account, ownership and the full diff. Then regenerate and review the retirement
   plan to reflect completed cleanup; never reuse the stale plan.
10. Review the routing change set. Execute it with the recent `--receipt` and
    refreshed `--retirement-plan`; these are required even for a new/empty stack.
    The command re-verifies candidate state and coverage before execution. Wait
    for stack completion, confirm the new email subscription, then run
    `verify-routing`. Update/restart the customer's UI with the AgentConnection
    output and assume the generated UI role. Verify the UI separately.

Use `.venv/bin/python -m infra <command> --help` for exact arguments. For example:

```bash
.venv/bin/python -m infra change-set --bundle .local/release --stage tools --review-hash <bundle-hash> --output .local/tools-change.json
.venv/bin/python -m infra inspect --bundle .local/release --stage tools --review-hash <bundle-hash> --change-set <change-set-arn> --output .local/tools-diff.json
.venv/bin/python -m infra execute --bundle .local/release --stage tools --review-hash <bundle-hash> --change-set <change-set-arn> --change-set-hash <diff-hash> --output .local/tools-execution.json
```

`coverage` and `verify-routing` are read-only. `upload`, `change-set`, `execute`,
`prepare-agent`, `seal` and `retire` mutate AWS. `verify-candidate` performs the
explicit paid canary; `collect` reads outputs. `render` and `build` are local.
No command sends customer email except the routing deployment creates/changes
SNS subscriptions, which may send confirmation messages, and subsequent alerts.

`verify-routing` checks the exact event pattern, target, confirmed subscribers and
required alarm descriptors/actions. It does not prove message delivery. Updating
the shared foundations can change telemetry filters and log destinations; review
that migration separately from creating a candidate. Do not apply a changed
foundation inventory to an active environment as an unreviewed draft experiment.

## Promotion, rollback and remaining limitations

Each new release has a new agent as well as new functions. Preparing its draft
cannot change the active agent. Qualified versions are the default. If staging
proves that Bedrock cannot execute qualified ARNs for the selected integration,
choose executor_mode=release-name in a **new** candidate; never silently fall back.
The names remain release-specific, the stack is sealed, and verification compares
LATEST to its published snapshot. This fallback is operationally protected, not
intrinsically immutable against a privileged direct Lambda update.

Preserve release stacks, policies, Lambda grants/versions, agent aliases, secret
labels and artifact versions for at least rollback_days (default example: 14).
No automatic garbage collector deletes them. Retention attributes preserve data
and candidate dependencies on removal, but the supported rollback is to keep the
complete sealed stacks, not delete and reconstruct them. Stack policies are an
accidental-update guard, not a substitute for IAM; an administrator can override
protection. Audit direct mutations and drift before production qualification.

Rollback uses the previous private bundle and its implementation revision, a new
passing candidate/coverage receipt and a reviewed routing diff. Never edit an old
candidate stack or remove its grants to implement rollback. Change the UI connection
back along with incident routing. A removed recipient must reconfirm if required.
Review inventory differences: rollback is not permission to re-enable retired hosts.

SNS subscription replacement and UI reconfiguration are not one atomic operation.
A subscription transition can produce overlap or a delivery gap; a new email is
not usable before confirmation. Phase 3 owns durable ingress, deduplication,
independent initial alerting and recoverable delivery. Phase 2 does not make the
current direct worker lossless. Strict canary trace parsing may need adjustment
against real Bedrock responses; until validated it fails closed.

Gate G2 needs a real staged candidate invocation, isolation/IAM negative tests,
failed-grant preservation, retirement verification and rollback evidence. Template
lint and mocked policy tests do not establish those facts. G1 hosted CI must also
run before a production release is qualified.
