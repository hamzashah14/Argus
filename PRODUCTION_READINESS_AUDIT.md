**AIOps Assistant / Kira — production readiness audit and implementation plan**

Audit date: 1 October 2026. Verdict: **not ready to serve as the sole production incident detection and reporting system.** The application has useful defensive checks, but incident delivery, deployment isolation, monitoring coverage, and access control need work before production sign-off.

This audit covers all 20 current project files: Streamlit UI, three Lambdas, deployment/configuration scripts, IAM policies, alarm setup, OpenAPI schemas, agent instructions, telemetry examples, dependencies, documentation, and sample data generation. It evaluates the current working tree, including existing uncommitted and untracked files. Application code and AWS resources were not changed. This report is the only project file added by the audit.

The actual AWS deployment, Render service, instance configurations, credentials, quotas, model access, subscription confirmations, and real notification delivery were not inspected. Findings below distinguish locally reproduced defects, defects apparent in code, and production controls that are missing. A repository review cannot certify those live services.

**Validation performed.** All six Python files parse, all five shell scripts pass `bash -n`, and all three JSON files parse. All 21 existing Lambda self-checks pass using Python 3.12.14 and boto3/botocore 1.43.106 in an isolated dependency environment. A targeted OpenAPI array check found the contract violation in F20; JSON parsing alone does not validate an API contract. Additional mocked checks reproduced the cases identified below. These checks made no AWS API calls. Streamlit was reviewed statically; browser testing, dependency vulnerability scanning, IAM integration testing, load testing, and live fault injection remain outstanding.

Useful existing controls include the password configuration requirement, constant-time password comparison, instance and log-prefix validation, query escaping, query-window limits, old-metric period adjustment, scoped tool invocation permissions, explicit model/monitor regions, and tests for several happy and error paths. These are worth retaining.

Priority definitions: **P1** blocks production reliance or safe production releases; **P2** is required hardening/correctness work before broad rollout. No confirmed P0 emergency was established without a live deployment inspection.

For F20, array schemas require an item definition. [OpenAPI 3.0 Schema Object](https://spec.openapis.org/oas/v3.0.3.html#schema-object).

For F01, the SDK documents connection/read timeouts rather than a complete investigation deadline; SDK retries must also fit the application budget. [Botocore configuration reference](https://docs.aws.amazon.com/botocore/latest/reference/config.html).

For F02/F03, AWS documents duplicate asynchronous delivery and discarding expired or exhausted events unless a recovery destination is configured. The code's zero function-error retries do not eliminate duplicate delivery or throttling retries. [Lambda asynchronous error handling](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-error-handling.html).

For F04, unqualified Lambda invocation uses the mutable unpublished version; published versions provide immutable code/configuration snapshots. [Lambda versions](https://docs.aws.amazon.com/lambda/latest/dg/configuration-versions.html).

For F09, a successful HTTP response from PutTargets can contain failed target entries. [EventBridge PutTargets](https://docs.aws.amazon.com/eventbridge/latest/APIReference/API_PutTargets.html). For F13, SNS's ordinary publish limit is 262,144 UTF-8 bytes. [SNS Publish](https://docs.aws.amazon.com/sns/latest/api/API_Publish.html).

**Recommended implementation sequence.** The estimates below are planning estimates for one engineer familiar with AWS, assuming one account/region pair and a small static EC2 fleet. Allow roughly 12–19 engineering days plus a staging soak; account access, SSO, or organizational requirements may extend this. Implement and verify each phase before moving the release gate.

A suitable target flow is: alarm/event → durable incident intake → initial notification and queued investigation → bounded worker → durable result → independently retried follow-up notification. Use an incident store for state and deduplication, and restricted object storage for larger evidence. SQS plus a conditional-write store is a practical option. Step Functions becomes useful if investigations need checkpoints or routinely exceed one worker's safe time budget; it is not necessary to rewrite the whole project immediately. Retain Bedrock and Streamlit where they meet the revised requirements.

**Required release evidence.** Agree concrete targets before testing. A reasonable starting proposal is initial notification within 60 seconds of receiving the alarm event and either a completed or explicitly degraded investigation within 10 minutes. These are proposed acceptance targets, not measurements or guarantees. Detection delay is separate: the current CPU alarm itself requires roughly 15 minutes of elevated data.

- Duplicate/replayed records must converge on one incident and avoid repeating completed model work. Where a notification transport can still duplicate after ambiguous acknowledgement, include a stable incident/report ID and document that behavior rather than promising exactly-once email.
- Inject model denial/throttling, delayed chunks, stalled connections, Logs Insights failures, and notification failure. Every accepted incident must either complete, remain retryable, or land in a visible recovery state with its evidence retained.
- Exercise loss of the web listener, a hung process, Nginx failure, no traffic, failed log shipping, and missing CWAgent metrics. Confirm that “healthy” and “telemetry missing” remain distinguishable.
- Send real staging CloudWatch and EC2 events through EventBridge/SNS. Verify topic policies, Lambda permissions, subscription confirmation, actual email delivery, and the fallback route. Validate the EventBridge SNS SourceArn condition with the real integration rather than treating static policy text as proof.
- Test Unicode and oversized evidence, more than 250 groups, offsets/malformed dates, malformed tool parameters, supported/unsupported metric dimensions, and empty/failed model output.
- Simulate a failed target registration, denied metric discovery, interrupted deployment, removed instance, disabled alarm, and changed recipient. Deployment must not silently report complete coverage.
- Run at expected steady-state and burst incident volume with chat traffic present. Measure queue age, drop rate, query/model throttles, investigation duration, notification latency, and cost. Reserved concurrency alone is not a budget or throughput guarantee.
- Prove that deploying tool code does not alter the live agent until promotion, and that rollback restores the exact prior tools, schemas, configuration, and agent version.
- Run login/session/revocation tests and model evaluations with secret-bearing and hostile logs. Verify operator attribution and access-controlled evidence retention.

**Additional operational cleanup.** Keep the sample-data script isolated to staging or an unmistakable test prefix: [sample generator:28](/Users/hamzashoaib/Documents/Side-hustles/AIOps-Agent/scripts/generate_sample_data.py:28) writes synthetic incidents into the discoverable instance namespace and sets the chosen sample group's retention to one day even if it already exists. Its message says the group expires, but retention expires events, not the group. Generate CWAgent configuration from the same environment settings to prevent `/aiops` and 30-day retention drifting from deployment configuration. Expand Nginx detection deliberately if 500/503 responses must be covered; the default access pattern only selects 502/504, and access/error events can count the same failed request twice. Document model/region/inference-profile compatibility and verify it with the actual deployed identity. Update claims that every report is always emailed, reruns fully reconcile state, and the agent alias alone isolates production.

The priority is dependable detection and delivery first, then safe promotion and access, then richer diagnosis. Production sign-off should be based on measured staging evidence and a rehearsed recovery path, not on the passing unit checks alone.
